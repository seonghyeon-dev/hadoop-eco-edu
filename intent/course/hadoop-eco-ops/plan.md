## 2. 제작 순서

모듈 하나씩 만들어 보여 주고, 승인받고 다음으로 간다. 자료 없이 만들 수 있는 모듈을 먼저 하고, 사용자 자료가 필요한 모듈은 뒤로 둔다.

| 단계 | 만드는 것 | 쓰는 도식 | 필요한 자료 |
|------|------|------|------|
| 0. 제작 틀 | 발표 HTML 틀(샘플 엔진 정리 — 단계 펼치기, `D` 도식 열기, 발표 메모, 인쇄 · 좁은 화면), `deck/build.py`, 공통 스타일 | — | 없음 |
| 1. M1 (3장) | 시범 모듈 — 제작 틀 · 도식 · 검수 흐름을 이 모듈로 확인한다 | D02 | 원천 종류(없으면 자리표시자) |
| 2. M3 (9장) | Spark · Tez · YARN, Tez와 Spark 비교 | D10 ~ D14 | Tez → Spark 전환 여부, queue 구성(없으면 자리표시자) |
| 3. M4 (16장) | HDFS · Hive · Iceberg, 전환 비교 | D03, D15 ~ D21 | 동시 적재 대상 · 이유(없으면 자리표시자) |
| 4. M2 (11장) | Airflow, 프로세스 역할 · 서버 배치 | D05 ~ D09 | DAG 동작 상세(사용자 작성 — 자리표시자로 먼저 만든다) |
| 5. M5 (14장) | 모니터링 화면 | D04, D12 ~ D14 | **화면 캡처 · 마스킹 기준, 접속 URL, 점검 기준** |
| 6. M6 (21장) | 장애 대응 | D22, D23 | **재시작 명령어(사용자 기재), 전달 대상, 장애 사례 · 대표 log, Trigger 조건** |
| 7. M0 · M7 (5장) | 표지 · 목차, 장애 대응 요약 · 용어집 · 질의응답 | D01, D22 | 앞 모듈 완료 |
| 8. 마무리 | 자리표시자 정리, 전체 검수, 회차 파일 빌드 | — | 남은 자료 전부 |

- M2를 M3 · M4 뒤에 두는 이유: M2는 DAG 동작 상세(사용자 작성)가 많이 걸려 있다. 그사이 사용자가 작성할 시간을 둔다
- 도식 도구: archify를 기본으로 하고, dashmotion 후보(D02 · D08 · D13)는 그 도식을 만들 때 dashmotion을 써 볼지 정한다. dashmotion을 처음 쓸 때 설치 여부를 묻는다

## 3. 모듈 하나를 만드는 방식

1. spec 5절의 메시지 · 비고로 슬라이드를 HTML로 만든다 — 요점은 → 단계, 발표 메모는 `N`
2. 도식은 `deck/diagrams/`에서 만들어 자동 검사(archify finalize)를 통과시키고, 발표 HTML에 넣는다
3. 모르는 사실은 `[확인 필요: …]`, DAG 동작 상세는 `[사용자 작성: …]` 칩으로 화면에 남긴다
4. 검수(4절)를 마치고 사용자에게 보여 준다 → 수정 → 승인 → 커밋 · push

## 4. 검수

| 검사 | 방법 |
|------|------|
| 도식 | archify `finalize` 자동 검사 통과, 캡처로 직접 확인 |
| 슬라이드 | 브라우저(headless Chrome)로 단계마다 캡처해 확인 — 글자 넘침, 겹침, 단계 순서 |
| 동작 | `D` 열기 · `Esc` 돌아오기, 단계 이동, 좁은 화면 · 인쇄에서 모든 단계가 펼쳐지는지, 스크립트 오류 없음 |
| 표현 규칙 | 슬라이드 본문(발표 메모 제외)에서 대상 지칭(수강자 · 교육생 · 비개발자), 범위 설명("~하지 않는다", "몰라도"), 구어 문구를 검색해 0건 |
| 사실 | as-is 사실은 intent · 사용자 답변에 있는 것만. 일반 개념은 Airflow 2.7 · Spark 3.5 · Hive 3.1 · Iceberg 1.6 · Hadoop 3.2 문서 기준. to-be(k8s) 내용 없음 |
| 게시 | `mkdocs build --strict` 통과(GitHub Actions), 게시된 페이지가 열리는지 |
